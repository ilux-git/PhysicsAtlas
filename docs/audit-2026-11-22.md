## 4. Findings

Severity reflects PROMPT-2 §4–§10, not cosmetic impact.

### P0-1 — One path status conflates computation, conditions and physics review

`findPaths` sets `status: 'valid'` when all conditions are confirmed and no warning remains
(`src/engines/paths/find.ts:305-313`). The formula review field is never consulted for this
result unless it is not `standard-form`. The UI translates `valid` as «допустимый»
(`src/ui/FindPathPanel.tsx:10`). No formula in the database has any expert review, yet the path can
still read as approved.

Additional duplication: `Equation` carries both the entity-level `review.status` and
`physicalReview` (`src/domain/types.ts:29-34,77-88`). Both use `standard-form` and both are
authored. A single boolean cannot represent three different questions.

Required outcome: separate computational status, conditions status, and physics-review status;
never let the word «допустимый» imply physical verification.

### P0-2 — `solveFor` silently discards a mathematical root

`src/engines/ast/solve.ts:130-136` handles `x² = c` by returning `sqrt(c)` and a note that the
non-negative root is chosen. Probe:

```text
9 = s²  ->  ok: true, ast: sqrt(9),
            preconditions: ["9 ≥ 0", "выбирается неотрицательный корень"]
```

The equation has two real roots (±3). PROMPT-2 §6 requires an explicit `multiple-solutions` result
when the model cannot represent both roots, not a silent choice.

### P0-3 — Display is not checked against the AST; the printer is unsafe

The validator only checks that the symbol strings appear in `displayLatex`
(`src/knowledge/validate.ts:240-263`). Probe: the valid equation `v = s/t` was given the display
`v = s + t`; `buildKnowledgeBase` returned **zero diagnostics**. Symbol presence does not prove
operator agreement.

The infix printer used by the path UI and the validator is not precedence-aware:

```text
(a+b)/c  ->  "a + b / c"      # wrong
a/(b/c)  ->  "a / b / c"      # wrong
(-a)^2   ->  "−a^2"           # indistinguishable from -(a²)
```

Required outcome: structural display validation and a parenthesising printer.

### P0-4 — Domain restrictions are lost outside the inverse path

The solver records constraints only while walking from the root to the target. Probe:

```text
solve v = t + sqrt(s) for v  -> ok, preconditions: []
solve v = t + 1/s      for v   -> ok, preconditions: []
```

The original equation requires `s ≥ 0` and `s ≠ 0`. Those restrictions never reach the path or the
condition UI. This contradicts the product's condition-preservation promise.

### P0-5 — `verified` is accepted without a criterion

`DerivationVerification` and the schema accept `'verified'`
(`src/domain/types.ts:116`, `src/domain/schemas.ts:192`), and `Inspector`/`DerivationView` have a
branch for it. No reviewer identity, date or procedure exists anywhere. Seed data uses
`structural`, so the label is unused today — but the type and UI promise a status the project
cannot justify.

### P1-1 — Implicit multiplication precedence is ambiguous

The parser gives juxtaposition the same precedence as `*` and `/`
(`src/engines/ast/parse.ts:145-161`). Probe: `a / b c` parses as `(a/b)·c`. The grammar does not
state this rule, and PROMPT-2 §5 requires a fixed rule with tests. The listed expressions
`-a^2`, `(-a)^2`, `a^-2`, `a^2*b`, `2*m*a`, `m a`, `ma`, `sqrt(a^2)`, `(a+b)/c`, `a/(b/c)` were
probed; most parse as intended, but the mixed division/adjacency case is under-specified.

### P1-2 — Alternative forms are weakly checked

`validate.ts` checks dimensions and symbol presence for alternative forms, but not their AST-to-
display agreement, and not that their variable set equals the primary form. `deriveEdges` builds
`appears_in` only from the primary AST. An alternative form could add a variable that the graph
never shows.

### P1-3 — No edge-type registry

`deriveEdges` emits edges by convention only (`src/knowledge/derive.ts`). Nothing checks that
`appears_in` is quantity→equation, `expresses` is equation→law, or that `derived_from` stays
equation→equation. The direction of `derived_from` (target→source) is tested but not declared as a
machine-enforced contract.

### P1-4 — `P = UI` lacks a context statement

Its only condition is `same-element` (`equations.json`). PROMPT-2 §10 requires distinguishing
direct current, instantaneous power and average AC power. The current description does not say
which of those the atlas models.

### P1-5 — Conditions are not attributed and can be “all confirmed” with a hidden constraint

Paths aggregate conditions but do not say which equation requires them, and an unmapped solver
precondition is a generic warning. After the P0-4 fix, a path could show every knowledge-base
condition confirmed while an unverified square-root restriction remains. The conditions status
must account for that.

### P1-6 — Documentation contradicts the code

| Document claim | Actual |
|---|---|
| path statuses «допустимый / условно допустимый / недопустимый» (`math-engine.md:92-95`, README) | path status mixes three questions and is exactly the P0-1 issue |
| `physicalReview` is an independent authored status (`knowledge-schema.md:96`) | duplicated with entity `review`, and `standard-form` says nothing about expert review |
| validator verifies display (`content-status.md:43`) | it verifies symbol presence only |
| derivation `verificationStatus` may be `verified` (`knowledge-schema.md:135`) | no criterion or data exists |
| `docs/ast.md:107` says the non-negative root is chosen | PROMPT-2 forbids this silent choice |

### P2-1 — Investigation gaps

- No «Назад» history: selecting another object loses the previous one.
- The map does not explain why a node is present (hop distance) and edge direction/kind is only
  a tooltip/legend.
- Find Path inputs reset when switching tabs; selected object context survives, tool context does
  not.

### P2-2 — Dimension/unit audit is not systematic

Tests exist for main conversions and some negative cases, but there is no operation matrix for
add/subtract, negative powers, dimensionless values, invalid factors/offsets, numeric path conversion
to a requested target unit, and a content-level guarantee that no cross-group conversion is exposed.

### Content observations (deferred to stage 8)

- Sources are textbook groups with an explicit “pages/edition require verification” note. This is
  honest but incomplete; no page/ISBN facts are invented.
- Level texts exist for every quantity/law/condition; a quality pass is required after the engine
  fixes.
- `A = Fs`, `F = ma`, `v = s/t` have appropriate caveats; `P = UI` is the main content gap.

## 5. Audit conclusion

The maintained features are real: the app builds, runs, validates and has meaningful tests. The
defects are semantic, not cosmetic: the product currently overstates what a computed path proves,
can silently drop a root and a domain restriction, and accepts a display that contradicts its AST.

The approved remediation order is in [`plan-prompt-2.md`](plan-prompt-2.md). No expansion of the
knowledge base will start until the P0 items are fixed and the four commands pass after each stage.
